# DBへのアクセスは ORM を使わず、DBクラスのクエリビルダで書く

FuelPHP 1.8 の ORM パッケージ（`Orm\Model`）と比べたうえで、使わないことにした。Model は普通のクラスにし、中では DBクラスのクエリビルダ（`DB::select`・`DB::insert`・`DB::update`・`DB::delete`）だけを使って、結果は配列で返す。ORM はテーブルの1行をオブジェクトとして扱い、リレーションや保存をまとめて書ける。一方クエリビルダは、SQL の形をメソッドで組み立て、値はバインドする。このアプリのクエリは集計とロックが中心で、ORM の便利さ（リレーション、オブジェクトの保存）を使う場面が少ない。

## 理由

- **課題条件 No.7**：「データベースとのやり取りはDBクラスを使うこと」。ORM は別のパッケージ（`fuel/packages/orm`）で、中で DBクラスを使うものの、アプリのコードからは DBクラスを使っていることが見えない。クエリビルダなら、条件を満たしていることをコードでそのまま示せる
- **集計が多い**：ボード一覧の「カードの件数」（LEFT JOIN と COUNT）、選考ステージ別の人数（GROUP BY）、カードを追加するときの並び順（`COALESCE(MAX(sort_order), -1) + 1`）は、ORM で書いても `DB::expr()` やクエリビルダを混ぜることになる
- **カードの移動でロックが要る**：同じボードの移動を順番に処理するため、ボードの行を `SELECT ... FOR UPDATE` でロックし、並び順の振り直しとカードの更新を1つのトランザクションで行う（`Kanban\CardMover`）。FuelPHP 1.8 は ORM にもクエリビルダにも FOR UPDATE を付ける方法がない（`fuel/core/classes/database/` と `fuel/packages/orm/` を grep して確認）。この1か所だけ `DB::query()` で SQL を書き、値は `param()` でバインドする
- **権限の確認を1か所に集める**：Model のメソッドはどれもユーザーIDを受け取り、`Model_Board::can_access()` で確かめてから読み書きする（設計書4章）。ORM の `find()` はIDだけで誰のボードでも取り出せるので、取り出し方が増えるほど確認漏れが起きやすい

## Considered Options

- **ORM（`Orm\Model`）を使う**：リレーション（ボード → カード）、作成日時・更新日時を自動で入れる Observer、保存前の Validation が使える。ただし上の集計とロックは結局クエリビルダか SQL で書くことになり、2つの書き方が混ざる。作成日時・更新日時を入れるのは、ボードとカードの作成・更新の数か所なので、手で書いても手間は小さい
- **`Model_Crud` を使う**：1テーブルの CRUD はまとめて書けるが、JOIN・集計・ロックはできず、ORM と同じく書き方が混ざる
- **すべて `DB::query()` で SQL を書く**：自由に書けるが、値の埋め込みを間違えると SQL インジェクションになる。レビューでもよく「query ではなく select などを使いましょう」と言われる。クエリビルダで書けないロックの1か所だけにする
